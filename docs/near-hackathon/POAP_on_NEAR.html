The problem

  • Proof-of-attendance badges usually ask guests at the door to install a wallet, approve a popup and pay gas.
  • Most give up, so the badge never reaches them, and the organiser is left with a list of addresses and no names.
2

What we built

  • An organiser creates an event on poap.live and chooses NEAR or XRPL.
  • Attendees register with a name and email and get an Apple Wallet pass, or use the POAP phone app.
  • The desk scans the pass and a soulbound badge is minted straight into the attendee's NEAR account.
3

How NEAR fits

  • One NEP-171 contract for every event; transfers refused, only the holder can burn.
  • The server holds a function-call key that can only call nft_mint.
  • Implicit accounts receive badges without being funded first.
  • attendance(event, account) stays on chain even after a burn.
4

The flow on NEAR

CREATE
Pick NEAR
The server draws an event id the contract has never used. The chain is fixed for good.
REGISTER
Name and email
On the website with a NEAR account, or in the app, which signs with its own key. The Wallet pass goes out by email.
SCAN
One transaction
The desk scans the pass; the server mints with its mint-only key. No offer, no accept, no gas for the guest.
PROVE
On chain
The badge is in their account, in Meteor or the app. Anyone can read the attendance record.

6

Built in the hackathon window

  • The badge contract (Rust, near-sdk), soulbound and upgradable, with deploy, upgrade and end-to-end scripts.
  • NEAR as a second chain across the server, organiser console, desk, registration and pass pages.
  • Apple Wallet passes for every registration: signed, emailed, a QR code that changes on every scan, updates pushed to the phone.
  • NEAR in the phone app: the same key as a NEAR account, badges read from the contract, the key exportable to Meteor.
  • Deployed to mainnet as poap-live.near; 1,106 server tests and 31 contract tests.
